# Contract Surfaces

Registry of load-bearing names and contracts that must remain consistent across the project.

- `/dashboard` is the server-rendered, protected recipe collection entry point and the destination after successful login and a confirmed product import. Missing or invalid users receive a 302 redirect to `/auth/signin`; unavailable authentication infrastructure returns 503. The PDF import CTA appears only when `PDF_IMPORT_ENABLED=true` and the required production infrastructure is configured outside preview.
- `/dashboard?page=<positive-integer>` lists at most 24 recipes visible through the signed-in user's RLS session, ordered by `created_at DESC` and then `id ASC`. Missing `page` means page 1; malformed and out-of-range pages share the collection-page 404. Query parameters, including `owner_id` and `user_id`, never select the collection owner.
- `/dashboard/recipes/<uuid>` reads one recipe through the signed-in user's RLS session. A malformed UUID, a nonexistent UUID, and another owner's UUID share the same 404 status and neutral `Przepis niedostępny` view without disclosing the identifier, title, or reason. Database/read-contract failures remain a separate 500 state. The route accepts no owner identifier.
- `/dashboard?import=<uuid>` accepts only a UUID, removes `import` from the visible URL and fetches `/api/imports/<uuid>` before displaying saved and already-existing counts. The API status is owner-scoped; URL-supplied counters, invalid IDs and another owner's IDs never populate the banner.
- Product PDF rollout applies `20261009120000_product_pdf_import.sql` before application code, deploys the code with `PDF_IMPORT_ENABLED` absent or `false`, verifies F-01 and owner-scoped status, then enables the flag only in production. Rollback disables the flag, which blocks new imports while existing imports can finish or be cancelled and saved recipes and cost-ledger entries remain intact.
- Incomplete-recipe rollout applies `20261014120000_incomplete_recipe_decisions.sql` before application code, then deploys with `PDF_IMPORT_ENABLED=false`. Resolution of an already-created product import remains available through database-only infrastructure while new creation is disabled. Rollback disables creation first; existing recipes and content-free decision metadata remain valid and require no destructive down migration.
- `POST /api/imports/:importId/decisions/:decisionId` is an authenticated, same-origin, product-only keep/discard mutation. A keep carries the current tab's canonical candidate; discard carries no candidate content. Same-action replay returns the stored result, the opposite action returns `409 decision-conflict`, a digest mismatch returns `409 decision-payload-mismatch`, and missing, cross-owner, cross-import, or cross-channel resources use the non-disclosing not-found response. Status and decision rows expose references and counters, never pending candidate content or either digest.
- Pending incomplete content exists only in the active browser tab. Each durable decision is owner/import/source scoped and stores a domain-separated `canonicalDecisionDigest` over owner, import, recipe schema/contract, and the canonical reconciled candidate. The legacy batch-bound `digestValidatedCandidate` remains a separate digest domain with unchanged signature, payload, algorithm, and F-01/finalization callers.
- Kept incomplete recipes retain mandatory filename, nonempty pages, and source-start identity. `title` is null iff `missing-title` is current; `category` is null iff `missing-category` is current; instructions are empty iff `missing-instructions` is current; ingredient groups are empty or contain an empty ingredients array iff `missing-ingredients` is current. `absent-servings` implies null servings and `absent-footnotes` implies empty footnotes, but the reverse implications do not apply. `missing-continuation`, `missing-ingredient-content`, and `missing-variant-content` are semantic and may coexist with nonempty content. Omission arrays contain known, unique codes in canonical order, and `missing-source-metadata` is forbidden for saved recipes.
- `incomplete_at_import`, `import_missing_reason_codes`, and `kept_from_decision_id` are immutable import provenance. At the first keep, import and current omission arrays are equal. `category = null` is an explicit exception to the exactly-one-category rule only for a recipe created by a successful product keep whose immutable import omissions include `missing-category`; automatic, evaluation, backfill, and other writes still require one category.
- `kept_from_decision_id` identifies only the origin decision that first created an incomplete recipe. A later keep for the same owner and stable source identity may deduplicate to that recipe while retaining the recipe's original `import_id`, origin decision, and owner edits; the later decision may reference the existing recipe without import-ID equality.
- The legacy `finalize_pdf_validation_import(uuid, uuid, text, jsonb, jsonb)` signature and six-column result, `get_pdf_validation_import`, evaluation-channel behavior, and the service-role-only eleven-column `get_pdf_import_recipes(uuid, uuid)` result, ordering, and grants remain contract-compatible.
- `App.Locals.user` is request-local identity populated by `supabase.auth.getUser()`. Query parameters, including `user_id`, never select the current account.
- Every response passing through session middleware carries `Cache-Control: private, no-store`, including personalized `/`, protected HTML, authentication redirects and infrastructure-unavailable responses. Preserve response status, Location, body and all session cookie updates.
- `/api/ops/deployment-probe` bypasses session handling and retains its independent bearer-token authorization and cache policy.
- Recipe collection and detail reads are owner-scoped by the cookie-bound Supabase client plus RLS; import reads remain owner-scoped by authenticated status APIs. Future filtering must preserve those ownership checks.
